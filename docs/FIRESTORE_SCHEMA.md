# Firestore Schema

Field lists describe the current application contract. Some documents may contain additional timestamps or UI-support fields.

## `users/{uid}`

Purpose: account identity and role routing.

Typical fields:

```text
uid
firstName
lastName
name
email
phone
role: patient | doctor | admin
approved
isActive
profileImageUrl
loginMethod
createdAt
updatedAt
```

Patient favourites are stored as:

```text
users/{patientUid}/favorites/{doctorUid}
```

## `doctors/{doctorUid}`

Purpose: doctor discovery, approval, profile, and availability.

```text
uid
name
email
phone
specialty
designation
qualification
experienceYears
hospitalName
bio
approved
available
availableSlots: [string]
averageConsultationMinutes
profileImageUrl
createdAt
updatedAt
```

## `appointments/{appointmentId}`

Purpose: patient-doctor booking lifecycle.

```text
patientId
patientName
doctorId
doctorName
specialty
appointmentDate
scheduledAt
time
symptoms
preVisitNotes
notes
status
slotId
startedAt
completedAt
createdAt
updatedAt
```

Common statuses:

```text
Pending
Accepted
Rejected
In Consultation
Completed
Cancelled
```

## `appointment_slots/{slotId}`

Purpose: deterministic double-booking guard.

```text
doctorId
dateKey
time
booked
appointmentId
patientId
updatedAt
```

The document ID is based on doctor, date, and time.

## `health_profiles/{patientUid}`

Purpose: patient health summary and doctor access list.

```text
uid
height
weight
bmi
bloodGroup
allergies
conditions
doctorIds: [doctorUid]
emergencyContact
updatedAt
```

Doctors can read a profile only when their UID is included in `doctorIds`, subject to Firestore rules.

## `prescriptions/{prescriptionId}`

```text
patientId
doctorId
patientName
doctorName
medicines: [string]
doctorNotes
notes
createdAt
```

## `medicines/{medicineId}`

```text
patientId
name
dosage
frequency
time
taken
createdAt
updatedAt
```

Medicine reminders are currently represented in app data and notifications; operating-system-level scheduled reminder reliability must be separately implemented and tested for a production version.

## `timeline_events/{eventId}`

```text
patientId
type
title
details
appointmentId
prescriptionId
createdAt
```

Examples:

```text
appointment_booked
appointment_completed
prescription_added
```

## `notifications/{notificationId}`

```text
userId
title
message
read
createdAt
readAt
```

## `announcements/{announcementId}`

```text
title
message
createdBy
createdAt
```

Announcements are shown to authenticated users.

## `messages/{messageId}`

```text
conversationId
participants: [uid, uid]
senderId
receiverId
senderRole
text
sentAt
isRead
```

The conversation ID is generated by sorting the two user IDs and joining them.

## `call_requests/{requestId}`

```text
requesterId
receiverId
status
createdAt
updatedAt
```

This records a request; it does not provide a real voice/video call service.

## `reviews/{appointmentId}`

Purpose: one review per completed appointment.

```text
appointmentId
patientId
patientName
doctorId
doctorName
rating
comment
createdAt
updatedAt
```

Using the appointment ID as the review document ID prevents multiple review documents for the same appointment.

## `symptom_rules/{ruleId}`

```text
symptoms: [string]
department
urgency
advice
enabled
createdAt
updatedAt
```

Admins can seed defaults and edit these rules without changing Dart code.

## `emergency_requests/{requestId}`

```text
userId
userName
role
status: Open | Resolved | other admin-managed status
latitude
longitude
handledBy
createdAt
updatedAt
```

Location may be absent when permission is denied or positioning fails.

## `hospitals/{hospitalId}`

Suggested fields:

```text
name
address
phone
latitude
longitude
isOpen24Hours
services: [string]
```

## Collections referenced by rules but not central to the current UI

- `health_cards`
- `emergency_contacts`

Keep rules and data contracts synchronized if these are expanded later.

## Timestamps

Use Firestore server timestamps for creation and update metadata whenever possible. Avoid storing sortable dates as display strings.
